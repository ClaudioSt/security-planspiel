### Locked Decisions

**Risk register (new first Teamheft page)**
- **D-01:** The register has **5 rows (R1–R5)**. That is enough to cover all later attacks while still forcing a choice.
- **D-02:** Columns per risk:
  - asset ("what is valuable?");
  - threat or weakness, with the source document;
  - protection goal **C / I / A** (the core of the CIA learning goal);
  - business-impact **category tick**, plus **one sentence**. Candidate categories: production stop, main customer/OEM, know-how, costs; final wording is at Claude's discretion;
  - **rank 1–5**;
  - **treat / accept** tick, plus one line of reasoning;
  - **Rückblick** after wave 3: correctly rated, underestimated or overestimated.
- **D-03:** Likelihood × impact is assessed in a **3×3 risk matrix** printed on the same page, which the user found illustrative. Teams write the risk numbers (R1–R5) into the cells.
  - The matrix has **colour zones** (red, yellow, green).
  - The **rank column** in the table gives an unambiguous order for budget prioritisation.
- **D-04:** The matrix's impact axis is labelled with **€ bands for low, medium and high**.
  - The bands are numbers, so they live in `simulation_config.json` (new block) and never in prose.
  - They must be realistic relative to the game's damage values: an unprotected attack costs 140,000–320,000 €, and the worst case is 620,000 € in total.
  - The planner proposes the exact limits from the game values. A starting point: low < 50,000 €, medium 50,000–150,000 €, high > 150,000 €.
  - The validator checks the bands, ascending and non-overlapping.
- **D-05:** Teams may **ask the facilitator what a damage would mean for the business**. This is the user's chosen communication practice: secondary goal, but welcome.
  - The facilitator answers with a **€ order of magnitude** from the bands, in the role of MechTech's management.
- **D-06:** The facilitator booklet gets a **cheat sheet of 6–8 typical business cases**, each with an answer and a band.
  - Examples: "production stops for a day", "design data ends up with a competitor", "the OEM puts orders on hold".
  - Cases are phrased as **business consequences, never as attacks**, so nothing is revealed. The figures come from config, the prose from `texte.toml`.

## Summary

The phase is pure print material and flow work on a mature, heavily-linted pipeline. Every number must come from `simulation_config.json`, every word from `content/texte.toml`, print models hand finished strings to templates, and the veil/digit/fill/stamp checks are enforced by tests. Nothing needs a new library. The hard parts are not technical novelty but *coupling*: ten plans edit overlapping files (`content/texte.toml`, `planspiel/texts.py`, `simulation_config.json`, `planspiel/booklet.py`, `print/templates/master.tex.j2`, `tests/test_intro_deck.py`), the deck is an 81 MB binary behind a human approval gate, and the deadline is 13 days away with three human gates (deck checklist, deck review, printed approval).

Key findings the planner can rely on. (1) The register **does fit one A4 portrait page**: a prototype built with the real `planspiel.sty` (5 rows at 18 mm, example row, 3×3 matrix, instruction) used 669.6 of 731.2 pt, so no landscape page is needed (and the booklet PDF test pins A4 portrait). (2) The € bands should be **low < 50 k, medium 50–150 k, high ≥ 150 k** (thousand-€ in config like `s_unit` and budgets): the three unprotected damages 140 / 160 / 320 k land in medium / high / high, no damage sits on a limit, and the residual damages of within-budget plans spread over all three bands. (3) A trap: `tests/test_single_definition.py` forbids reading `.base_severity` / `.s_unit` outside `rules.py` and `config.py`, so the "unprotected damage" needed for band checks must come from a new one-line `rules.unprotected_damage()` that `rules.base_losses` also uses. (4) A plain python-pptx save of the committed deck is **not** byte-stable (measured: it renames the closing slide part, rewrites `<a:t></a:t>` in slide 1, touches notes rels), so the deck must be assembled by the surgical zip patch used in 07-09, now with one added slide part. (5) New text keys must be conditional on `cfg.risk_matrix` (like `practice`/`session_schedule`), otherwise `tests/fixtures/mini_content/texte.toml` must be edited too.

**Primary recommendation:** Order the plans 01 → 08 (with a strict-xfail bridge on two deck-test cases) → 02 → 03 → 04 → 06 → 05 → 07 → 10, run RISK-09 (deck, human gates, disjoint files) alongside from the second wave on, treat `texte.toml` / `texts.py` / `simulation_config.json` as single-writer files, keep all new text keys conditional on `risk_matrix`, and write the committed print set only in RISK-10.

### Pattern 1: Optional block, absent in the mini fixture
**What:** A new top-level config block is loaded as `Optional[...] = None` at the end of `Config`; every model returns `None` / skips the element when it is absent; text keys are required only `if cfg.risk_matrix is not None`.
**When to use:** all RISK models. Precedent: `practice` (`config.py:250`), `session_schedule` (`config.py:262-281`), `texts.required_keys` conditionals (`texts.py:385`, `texts.py:389`).
**Why it matters here:** `tests/fixtures/mini_config.json` has no `session_schedule`/`practice`/`risk_matrix`, and `tests/fixtures/mini_content/texte.toml` carries **all unconditional** `SHEET_KEYS`. A new unconditional key (e.g. in `_TEAMHEFT_KEYS` or `SHEET_KEYS`) forces an edit of the mini content; conditional keys do not. The booklet tests run `mini` and `real` (`tests/test_booklet_render.py:21-24`).

**Example (loader + isolation proof, mirrors `tests/test_session_schedule_config.py:95-110`):**

### Pattern 3: Strict xfail bridge
**What:** mark exactly the deck-test cases the schedule change breaks `@pytest.mark.xfail(strict=True, reason="RISK-09 deck edit pending")`; the deck plan removes the marks in its RED commit and the green deck edit makes them pass. Strict means an XPASS fails, so the marker cannot be forgotten. Precedent: Phase 6 `TUNING_TARGET` / 06-10 re-pin (`STATE.md:193,195`).

### Anti-Patterns to Avoid

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| German number/money text ("50.000 €", "Rang 1 – 5", "60 Sekunden") | f-strings with manual dots | `fmt.format_number`, `fmt.format_money` (`fmt.py:25-60`) | exact formatting, thousands dot, true minus; used by every model |
| Unprotected damage per attack | `attack.base_severity * attack.s_unit` in a new module | new `rules.unprotected_damage()`; make `rules.base_losses` call it | the operand guard test; one definition |
| Per-page layout proof | eyeballing | `\fillreport{\thepage}` + `tests/support/pdf_text.FILL` + "no `Overfull \hbox`" assertion (`test_booklet_pdf.py:123`) | already enforced for every Teamheft page |
| Veil check of new text | ad-hoc grep | `veil.name_hits(text, ctx, audience.PROFILE_STORY)` over model fragments (`tests/test_schedule_model.py:146`) | same lint the print job gets |
| Page fragments of a new page | custom walker | dataclass + `printed_strings()` / `_fragments()` (`cards.py:116-129`) | new fields are picked up automatically by the PDF "text is on the page" tests |
| Deck slide numbers in tests | hard-coded new numbers everywhere | one named constant per slide plus (optional) a title-anchored lookup | the existing tests pin numbers; a lookup removes the next renumbering churn |
| Zone colours in grayscale | colour only | colour tint **plus** a printed zone word in each cell | prints readable on a mono laser; the level badges already carry a digit for the same reason |

**Key insight:** this codebase's value is that a stale number is impossible by construction. Every new figure (bands, row count, pitch seconds, case bands) must be a config value that a model formats; every new sentence must be digit-free prose.

## Common Pitfalls

### Pitfall 1: Operand attribute guard
**What goes wrong:** `test_no_formula_operands_outside_rules_and_config` fails the fast suite as soon as a new `planspiel/*.py` reads `.base_severity`, `.s_unit`, `.init`, `.opex`, `.weights`, `.bonus`, `.recovery`, ... (`tests/test_single_definition.py` `OPERAND_ATTRIBUTES`).
**Why:** one definition of every formula and operand access.
**Avoid:** add `rules.unprotected_damage(attack) -> int` (= `base_severity * s_unit`), make `base_losses` call it, use it from `risk.py`/`cheatsheet.py`; the validator uses raw dict subscripts. Optionally list the function in `FORMULA_FUNCTIONS`.
**Warning sign:** `AssertionError: ... .s_unit` naming your file.

### Pitfall 2: Unconditional text keys break the mini fixture
**What goes wrong:** `check_coverage`/booklet tests for `mini_config` fail with `texts.missing_key`.
**Avoid:** declare all new keys inside `if cfg.risk_matrix is not None:` in `required_keys`; models return `None` without the block.

### Pitfall 3: Orphan or missing keys
**What goes wrong:** `check_coverage` errors on any `texte.toml` leaf not declared in `texts.py` (`texts.orphan_key`) and on missing ones.
**Avoid:** edit the key tuples and `texte.toml` in the same commit; run `uv run planspiel texts`.

### Pitfall 4: Fill/Overfull on a narrow table
**What goes wrong:** `Overfull \hbox` in the log fails `test_the_build_log_has_no_missing_glyph_and_no_overfull_line`; a long unhyphenated word in a 13–23 mm cell overflows; a wrapped planning label adds ~4 mm per row.
**Avoid:** column sum ≤ ~149 mm for seven columns at `tabcolsep` 3 pt (prototype overflowed at 151 mm); compute label widths (Arial metrics) as done above; require fill ≤ `text` and no Overfull in each layout plan.

### Pitfall 5: Page-count and numbering pins
**What goes wrong:** `len(pages) == 4` (`test_booklet_pdf.py:42`), planning-first assertion (`:41-46`), "RoS follows tracking" (`:65-68`) and the review-last test fail legitimately; the PDF stamp test expects `Seite n von total` for 5 pages.
**Avoid:** update them in the RISK-02 RED commit.

### Pitfall 6: Golden re-pin forgotten or silent
**What goes wrong:** `tests/golden/worksheet_tex.json` hashes the three real worksheets; RISK-04 changes them.
**Avoid:** re-pin with `--update-golden` in GREEN only, state it in the commit body; practice sheet must stay unchanged (its own tests).

### Pitfall 7: Binary deck churn
**What goes wrong:** plain `Presentation.save()` changes ~7 parts incl. a renamed slide part; each binary commit adds ~81 MB to `.git`.
**Avoid:** surgical patch + zip-entry diff as the acceptance criterion; single commit after the user's review.

### Pitfall 8: Veil on new player-facing text
**What goes wrong:** register instruction/example or the worksheet line trips the story profile or hints at a mechanic; `scan_documents` fails the build.
**Avoid:** keep the example from another industry, forbid weights/thresholds, no attack words; run `veil.name_hits(..., PROFILE_STORY)` in model tests; the cheat sheet is facilitator-only but is spoken aloud before the waves, so test it with the story profile too.

### Pitfall 9: Prose-in-config and number words
**What goes wrong:** putting case descriptions or band labels into config trips `schema.prose_in_config`; spelling "fünf Risiken" trips the number-word lint.
**Avoid:** config holds ids, numbers, band ids; words live under `sheets.register.bands.<id>` / `sheets.cheatsheet.cases.<id>`.

### Pitfall 10: Rounding of the 150 k edge and exact bands
**What goes wrong:** inclusive/exclusive disagreement between axis label, `band_of` and Rückblick.
**Avoid:** one `band_of`, `min` inclusive, labels generated from the same list, validator forbids unprotected damage and case anchors on a limit.

```python
def unprotected_damage(attack: Attack) -> int:
    return attack.base_severity * attack.s_unit

def base_losses(waves, attacks) -> int:
    return sum(unprotected_damage(attacks[wave.attack_id]) for wave in waves)
```

### Band lookup
```python

def band_of(bands: tuple[RiskBand, ...], amount_k) -> RiskBand:
```
