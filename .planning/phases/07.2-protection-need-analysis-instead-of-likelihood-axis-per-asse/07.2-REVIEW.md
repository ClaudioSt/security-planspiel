## Summary

Reviewed the 07.2 source diff `f631752..HEAD`: the protection-need table that replaces the 3×3 likelihood × impact matrix, the per-case protection goal with its validator checks, the cheat-sheet goal column, the reworded texts and README, and the rewritten tests. The deck binary and the generated PDFs were not reviewed.

The core logic holds up when traced:
- `load_config` runs `validate` first (`check_config`), so a missing or invalid `asset_rows` or `goal` produces a `schema.keys`, `schema.range`, `schema.type` or `risk.case_goal` error and never a `KeyError` in the loader.
- `strongest_goals` handles ties correctly: ransomware gives {c, i}, ot gives {a}, exfil gives {c}. A non-int or malformed `cia_impact` is skipped safely because `cia_dict` already reports it.
- Non-string `goal` and `like_attack` values are guarded before any `in` test.
- `MAX_ASSET_ROWS` (4) matches the config value (4).
- The matrix-only code is gone: `zone_of`, `ZONES`, `MatrixCell`/`MatrixRow`, the likelihood and zone text keys, `example.cell` and the `risk*` colours. No reference to them is left in `planspiel/`, `print/`, `content/` or `README.md`.
- The in-scope tests pass: 361 passed, 3 skipped. `uv run planspiel validate` reports 0 errors.

There are no blockers. There are two warnings. The model test for the maximum-principle word cannot catch a wrong implementation. The D-12 rule that each of C, I and A has a case is only checked against the shipped config, not by the validator. The info items are about gaps between what `validate`/`texts` accept and what the print build accepts, leftover transitional or stale naming, and tests that match on substrings.

## Warnings

### WR-01: The maximum-principle test cannot catch a wrong "gesamt" computation

**File:** `tests/test_booklet_model.py:375` (implementation `planspiel/booklet.py:253`)
**Issue:** `test_the_need_example_follows_the_maximum_principle` uses the shipped example C = hoch, I = mittel, A = hoch. Its first rating is already the maximum, so the trivially wrong implementation `highest = rated[0]` passes. The test also recomputes the expected value with the same `max(..., key=index)` expression it is meant to check, so the test mirrors the code instead of checking it independently. The deck test (`tests/test_intro_deck.py`) has a second row where the maximum is not the first rating ("Speiseplan der Kantine" gering/gering/mittel), but it checks the hand-edited slide and not `booklet._register_page`. As a result, the only code-computed number-like value on the player page (the example's "gesamt" word) has no test that would fail if the code were wrong.
**Fix:** Add a model test with a patched `texte.toml` in which the maximum is not in the C position, and assert a literal expected word instead of recomputing it:
```python
def test_the_need_example_total_is_the_highest_band_not_the_first(tmp_path):
    source = (CONTENT_DIR / "texte.toml").read_text(encoding="utf-8")
    head, marker, tail = source.partition("[sheets.register.need_example]")
    tail = tail.replace('c = "hoch"', 'c = "gering"', 1).replace('a = "hoch"', 'a = "mittel"', 1)
    path = tmp_path / "texte.toml"
    path.write_text(head + marker + tail, encoding="utf-8", newline="\n")
    booklet = build_team_booklet(load_config(CONFIG_PATH), load_texts(path))
    assert booklet.register.need_example[1:] == ("gering", "mittel", "mittel", "mittel")
```
Add a second case with the order (mittel, gering, hoch) so that both `rated[0]` and a lexicographic `max(rated)` fail.

### WR-02: The D-12 coverage rule (C, I and A each have a case) is not enforced on candidate configs

**File:** `tests/test_risk_matrix_config.py:278` and `:320`; `planspiel/validate.py:718-782`
**Issue:** D-12 makes per-goal coverage the point of the integrity case: teams now ask per asset and goal, so a goal without a case leaves the facilitator without an answer. This rule is checked only by `test_every_protection_goal_has_a_case` and by `test_every_case_carries_a_goal_of_c_i_or_a`. Both run against the hard-coded `CONFIG_PATH` fixture, not the `--planspiel-config` candidate option. A candidate or edited config that drops `data_trust`, or retags it, passes `uv run planspiel validate` with 0 errors and builds a cheat sheet with no integrity case. The two tests also repeat each other: both assert `{case.goal ...} == {"c", "i", "a"}`, and `any(case.goal == "i")` adds nothing to that set equality.
**Fix:** Either add a validator check next to `risk.case_goal`, for example `risk.case_goal_coverage` (a warning is enough if D-12's "should" is meant as soft):
```python
goals = {case.get("goal") for case in cases if isinstance(case, dict)}
missing = CIA_KEYS - goals
if missing:
    self.warning("risk.case_goal_coverage", path, f"Kein Geschäftsfall für Schutzziel(e) {sorted(missing)}")
```
or move the coverage test into the `balance`-marked suite so it reads `--planspiel-config`. In both cases, remove the duplicated assertion from one of the two tests.

## Info

### IN-01: `planspiel validate` accepts an `asset_rows` value the page cannot print

**File:** `planspiel/validate.py:656`, `planspiel/booklet.py:40,235`
**Issue:** The validator only enforces `asset_rows >= 1`. A value of 5 or more passes `validate` with 0 errors and then fails at `planspiel print` with a `PrintModelError`. This mirrors the existing `register_rows`/`MAX_REGISTER_ROWS` and `MAX_CHEAT_CASES` split, so it is consistent, but the failure comes late in the pipeline.
**Fix:** Optional. Pass `hi=MAX_ASSET_ROWS` (and `MAX_REGISTER_ROWS`) to `int_field`. This needs the constants to move to a module that `validate` can import without pulling in print models. Otherwise, keep the split as it is.

### IN-02: Band words in `need_example` are checked only when the booklet is built

**File:** `planspiel/booklet.py:246-252`, `planspiel/texts.py:219`
**Issue:** `check_texts` only checks that the keys `sheets.register.need_example.{asset,c,i,a}` exist. A value that is not a band word (for example "riesig") passes `uv run planspiel texts` and fails at `planspiel print`.
**Fix:** Add the band-word check to `check_texts` when `cfg.risk_matrix` is present, or accept the print-time stop as the gate.

### IN-03: `strongest_goals` uses the absolute value, so a positive `cia_impact` counts as "most strongly hit"

**File:** `planspiel/validate.py:785-792`
**Issue:** `cia_dict` allows any integer, and `rules` applies `severity * impact`. A positive entry would raise CIA, yet `abs()` would rank it as the strongest "hit" goal. No shipped attack has a positive entry, so this is latent.
**Fix:** Rank by `-value` (most negative is hit hardest), or document that `cia_impact` entries are never positive and add a `lo`/`hi` bound in `check_attack`.

### IN-04: The cheat-sheet header keeps its transitional shape, and the column order is split between model and template

**File:** `planspiel/cheatsheet.py:39-40,71-72`, `print/templates/master.tex.j2:109`
**Issue:** `header` is still the 3-tuple (case, answer, band) with a separate `goal_header`. The 07.2-03 summary says this was a bridge "until the template grows the column". The template now grows the column and places the goal itself with `header[0]`, then `goal_header`, then `header[1:]`. The column order is therefore defined partly in the template, and tests have to rebuild it (`tests/test_master_pdf.py` unpacks `head_case, head_answer, _`).
**Fix:** Make `header` a 4-tuple (case, goal, answer, band), drop `goal_header`, and go back to the plain `for cell in sheet.cheat.header` loop in the template.

### IN-05: Stale "Risikomatrix" / "risk matrix" wording outside texts

**File:** `planspiel/validate.py:654,663`, `planspiel/config.py:120`
**Issue:** The validator's German CLI messages still say "in der Risikomatrix" and "Die Risikomatrix hat genau … Bänder", and the `RiskBand` docstring says "band of the risk matrix". The block name is kept (D-15), but D-13 retires the matrix wording, and the README now calls the block "Schutzbedarf und Register (… der Name des Blocks ist historisch)".
**Fix:** Reword to "im Block risk_matrix" / "Der Block risk_matrix hat genau … Bänder" and "One € impact band".

### IN-06: Macro names chosen so substring tests still match

**File:** `print/planspiel.sty:105-116`; `tests/test_booklet_render.py:135-150` and the register-row test
**Issue:** `\tickboxsmall` and `\writelinecompact` were named so that `"\\tickbox"` and `"\\writeline"` substring checks keep passing, as the comment in the sty says. The render tests count `\tickbox` occurrences, so they cannot tell the 3.2 mm box from the 4 mm box, and a cell with a mix of both still counts as correct. Production naming is driven by test convenience.
**Fix:** Match with a regex that is anchored to the macro name, for example `re.findall(r"\\tickboxsmall\b", cell)`, and assert the exact macro the page needs.

### IN-07: The register example's goal and band link to the need example is loose

**File:** `content/texte.toml:438-440`, `tests/test_booklet_model.py:400-406`
**Issue:** `sheets.register.example.goal = "A"` is a literal that repeats `sheets.register.goals.a`, and nothing in the model ties it to the goal letters. The test finds the goal id with `next(...)`, which raises `StopIteration` instead of failing with a clear assertion when the letter changes. It then checks that the band word is a substring of the free decision sentence ("der Schaden wäre zu hoch"). Related weakness: `tests/test_intro_deck.py:288` asserts "no cell fill" only by the absence of `a:solidFill`, so a `gradFill`/`pattFill` or a table-style band fill would pass.
**Fix:** Give `next()` a default and assert on it, for example `goal_id = next((...), None); assert goal_id`. Either store the example's goal as an id (`a`) and map it through `goals` in the model, or keep the literal and assert that it is a value of `goals`. In the deck test, also reject `a:gradFill`, `a:pattFill` and `a:blipFill`.
