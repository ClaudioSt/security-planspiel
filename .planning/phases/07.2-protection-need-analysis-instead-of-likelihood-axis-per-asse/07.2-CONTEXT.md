# Phase 07.2: Protection-need analysis instead of the likelihood axis - Context

**Gathered:** 2026-11-22
**Status:** Ready for planning
**Source:** Conversation with the user (2026-11-21/22) plus four decisions taken with AskUserQuestion; no separate discuss-phase run (time before the dry run on 2026-11-25)

<domain>
## Phase Boundary

Phase 07.1 put a 3×3 likelihood × impact risk matrix on the first Teamheft page. The user's view: student teams cannot estimate likelihood, and in this deterministic game every attack happens, so the likelihood axis is guesswork and the Rückblick never grades it. This phase replaces the matrix with a **per-asset protection-need analysis** (Schutzbedarfsfeststellung in the style of BSI IT-Grundschutz). Teams list the assets they derive from the story and rate the damage per protection goal C, I and A in the existing € bands. Each register risk points to an asset and its main goal, so the risk's band is read from the table.

Print material, texts, config structure and the intro deck only. **No game formula and no balance value changes.** The € bands (D-24 of 07.1: below 50,000 €, 50,000 to below 150,000 €, from 150,000 €) stay. The set ships as **print release candidate 4** before the dry run on 2026-11-25. RC4 supersedes RC3.

</domain>

<decisions>
## Implementation Decisions

### Protection-need table (replaces the risk matrix)
- **D-01:** The 3×3 matrix with likelihood axis and colour zones (tragbar / abwägen / vorrangig) leaves the Teamheft. Nothing on a player page asks for a likelihood any more.
- **D-02:** It is replaced by a **protection-need table with empty asset rows W1–W4** (user choice "Leere Zeilen"). Teams derive the assets themselves from the story documents, which serves the learning goal "risks from the company". The number of rows is a config number in the existing `risk_matrix` block. Four rows is the starting point; the planner may choose a different count if the page needs it.
- **D-03:** Each asset row has a cell per protection goal **C, I, A**. In each cell the team ticks **gering / mittel / hoch**, the existing band words, with the € ranges from config shown once in the table head or a legend.
- **D-04:** **Maximum principle** (user choice "Maximumprinzip"): each asset row gets a column "gesamt", the highest of its three ratings. This replaces the colour zones as the at-a-glance priority. The register's rank column stays the order for budget prioritisation.
- **D-05:** The order on the page follows the method: protection-need table first, register second. A filled example row from the other-industry example (the clinic, D-07 of 07.1) is shown for the table as for the register.

### Register (stays, slightly changed)
- **D-06:** The register keeps five risks R1–R5. Its "Wert" column now references an asset row (**W#**) instead of free text. The free text moves to the table.
- **D-07:** The register's C/I/A column is the risk's **main goal**. A risk's band is **read from the table**: the cell of its asset (W#) in its main goal's column. The team does not rate the band twice.
- **D-08:** The other register columns are unchanged: threat plus source, business-impact category and sentence, rank, treat/accept with reason, Rückblick.

### Rückblick
- **D-09:** **Only the band is graded** (user choice "Nur das Band"). "Your band" is now the protection-need cell from D-07. Everything else stays as in 07.1:
  - Compare with the full damage without measures (D-20).
  - Take the largest full damage when several attacks hit (D-27).
  - A risk no attack hit counts as "überschätzt" (D-25).
- **D-10:** Whether the team chose the right protection goal is **not graded**. It is discussed in the debriefing. The existing C/I/A-versus-wave-weights question of RISK-07 is reworded so it starts from the protection-need table.

### Facilitator cheat sheet
- **D-11:** Teams now ask questions per asset and goal, for example "what if the design data became known / were falsified / were unavailable?". The facilitator answers with a band. Every cheat-sheet case gets its protection goal (C, I or A) printed next to it. The goal tag is a classification, so it belongs in config next to the case's band. The validator checks it is one of c/i/a. For a case anchored to an attack (`like_attack`), the goal must be one of that attack's strongest `cia_impact` goals. Ransomware ties C and I, and both are accepted.
- **D-12:** Each of C, I and A should have at least one case. Today no case covers integrity. The planner adds at most one integrity case, phrased as a business consequence and never as an attack, so the sheet stays within 6–8 cases. Its band must be consistent with the game values (D-22 of 07.1).

### Documents that follow
- **D-13:** Every text that names the risk matrix, the likelihood or the zones is reworded for the protection-need table:
  - the register instruction and review hint, and the cheat-sheet band title;
  - `README.md` (story step, material list, config block description);
  - the "Was ist neu" sheet, within its one-page limit;
  - the debriefing questions;
  - the booklet direction text for the story block.
  The change order of CLAUDE.md applies: config → README → texte.toml → print.
- **D-14:** Code that only served the matrix is removed, not left dead: `risk.zone_of`, `risk.ZONES`, the likelihood and zone words, and the zone colours if nothing else uses them. Tests that pinned the matrix are rewritten test-first for the table. `band_of` and `band_ranges` stay.
- **D-15:** The config block keeps its name `risk_matrix`, which avoids churn in loader, validator and tests, unless the planner finds the rename cheap and clearly better. Its README description is reworded either way.

### Intro deck
- **D-16:** Slide 32 "Risiko-Matrix" becomes a protection-need slide. It explains assets × C/I/A with gering/mittel/hoch, the maximum principle, and how the register reads its band from the table. It has no MechTech or attack content. The procedure is the same as 07.1 D-19 (Phase 7 D-18): python-pptx, edit run texts where possible, a checklist the user approves before the edit, user review of the result, and the deck test pinned to the new slide.

### Release and the 07.1 closure
- **D-17:** **07.1 closes without the paper check of RC3** (user choice "Ohne Papierprüfung"). Plan 07.1-10 is recorded with its build gates; the paper approval moves to RC4. The dry-run material record (07-DRYRUN.md "Material used") is written once, for RC4, by this phase's release plan.
- **D-18:** The release plan rebuilds the full set as **RC4**:
  - a clean stamp, `print --check` exit 0, and passing fast and pdf suites;
  - only `risk_matrix` may differ in the config, which is the no-game-value proof;
  - the user prints and approves before 2026-11-25, answering "Freigeben, Farbe", "Freigeben, Graustufen" or "Korrekturen: …".
  Colour vs. grayscale no longer depends on zone colours. The tick words carry the meaning.
- **D-19:** **Requirements** PROT-01..PROT-06 in `.planning/REQUIREMENTS.md`, one plan per requirement (user's global rule). Each plan updates README and "Was ist neu" for its own part where they describe what it changes (as 07.1 D-23).

### Claude's Discretion
- The exact layout of the table and register on one A4 page: column widths, tick size, where the € legend sits. The page must stay one page and pass the fill report.
- The German wording of all new texts, within the digit lint and veil rules.
- Whether the table's "gesamt" column is a tick set or a write-in cell.
- Whether the config rename of D-15 happens.

</decisions>
