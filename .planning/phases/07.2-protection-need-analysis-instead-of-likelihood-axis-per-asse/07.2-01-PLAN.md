<objective>
PROT-01: the `risk_matrix` config block carries the number of asset rows and a protection goal (c/i/a) per cheat-sheet case; the validator rejects a missing or unknown goal and, for a case anchored to an attack, a goal that is not one of that attack's strongest `cia_impact` goals; matrix-only code (zones, likelihood) is removed.

Purpose: the protection-need table (07.2-02) needs its row count from config, and the cheat sheet (07.2-03) needs a goal per case that the validator keeps consistent with the game's attack impacts. The likelihood axis leaves the game (D-01), so its code and words go now (D-14) instead of lingering as dead code.

Output: config block extended, loader and validator rules, the integrity case with its texts, matrix-only code and words removed, deck-test bridge, README parametrisation bullet, tests.

Decisions honoured: D-02 (asset rows as a config number, 4 rows), D-11 (goal per case in config, validator: one of c/i/a; anchored case goal among the attack's strongest goals, ransomware ties C and I), D-12 (one added integrity case, a business consequence, band consistent with the game values), D-14 (zone helper, zone constant, likelihood and zone words, zone colours removed; band_of and band_ranges stay), D-15 (the block keeps the name `risk_matrix`; a rename would touch loader, validator, texts, print models and many tests for no reader-visible gain; the README description is reworded), D-19 (README part of this plan).

Planner resolution of a conflict inside D-11 (flag for the user at the RC4 approval): today the ransomware anchor sits on `production_days` ("Die Produktion steht mehrere Tage still."), which is an availability consequence, but ransomware's strongest `cia_impact` goals are C and I (c −2, i −2, a −1). Tagging that case C or I would teach a wrong CIA mapping; tagging it A would break D-11. So the ransomware anchor moves to the one integrity case D-12 asks for (new id `data_trust`, band high, goal i), and `production_days` stays band high, goal a, without anchor (a plausibility case like `oem_hold`). The product rule "every wave attack anchors a case" (07.1 D-22) still holds. Goals of the unanchored cases (planner discretion): `audit_findings` c, `oem_hold` a, `production_day` a, `production_days` a, `single_pc` a. The case list is reordered by goal C, I, A so the facilitator finds a goal's cases together; the printed order follows config order. Plan-check note (W1/W2, orchestrator 2026-11-22): the 07.2-01-SUMMARY records the anchor move and gives a one-line rationale per case goal (why that consequence is mainly a C, I or A loss); the `like_attack` link is config data only and never changes the printed phrasing rule (business consequence, never an attack). The 07.2-06 approval question names the anchor move so the user approves it with RC4.

Hard rules: `uv run` only; numbers only in config, prose only in `content/texte.toml`; change order config → README → texte.toml; TDD with the RED commit first; no change to any value outside `risk_matrix`; `final_documents/generated/` is not touched (07.2-06 writes it); never stage `.claude/settings.local.json`; conventional commits with scope `(07.2-01)`.
